1　项目概述

1.1 我们要解决的问题

开完会之后的事情，通常比开会本身更耗人。一场一小时的评审会，散会后要有一个人回听录音、 整理纪要、把结论摘出来、把待办派下去，再在周报里复述一遍——这件事在中小团队里往往落在同一个人身上， 每次要花 40 分钟到 2 小时。更麻烦的是三个副作用：

  • 结论失真。整理者会不自觉地"顺"一遍逻辑，把"先看看"写成"已决定"，一周后没人说得清当时到底定了什么。
  • 待办蒸发。会上说"这个赵鹏跟一下"，落到文档里只剩一句"跟进相关工作"，没有责任人、没有时间。
  • 知识不沉淀。决议散落在聊天记录、文档、邮件里，三个月后新人问"我们的引用阈值是多少"，没人答得上来。

市面上的 AI 会议工具大多解决了"把话变成字"，但没解决"字能不能被信任"。我们做 AgentDesk 的出发点很朴素： AI 的输出必须能点回到原始证据。做不到这一点，纪要越快，团队越不敢用。

1.2 一句话定义

AgentDesk 是一个多 Agent 协同的办公平台：会议转写 → 带证据的纪要 → 可追踪的任务 → 周报 → 可引用的知识库， 全过程可审计、可回滚、成本可见。

1.4 立项时的三条自我约束

  1. 不假装模型永远正确。凡是模型给的结论，必须带得出原文引文；带不出就标"未决"，而不是硬凑一条。
  2. 不隐藏成本。每次调用都记 token、耗时、费用，界面上能查到每个 Agent 花了多少，用户能切"质量/均衡/成本"档。
  3. 不做成一次性演示。演示数据要能撑住评审，但真实链路必须能跑通——所以我们宁可花时间把延迟从 410 秒压到 30 秒，也不写死一份假结果。

2　需求分析

2.1 目标用户

我们把用户收窄到"5 到 30 人的产品/研发团队"。这个规模有三个特征：会多、没有专职 PMO、文档靠自觉。 再大的团队会有专门的会议系统，再小的团队不需要任务看板，反而都不适合。

角色核心诉求最在意的失败
会议组织者（产品/项目负责人）散会后 10 分钟内发出纪要和待办纪要被同事指出"我当时不是这个意思"
执行者（开发/设计）知道这周该干什么、什么时候交待办没有截止日，或者被人凭空指派
新成员快速问出"我们之前是怎么定的"AI 编一个看起来很像的答案
团队负责人看清这周产出、风险、谁的负载满了周报是流水账，看不出问题

2.2 需求从哪来

我们没有做大规模问卷，而是把自己日常的会议记录翻出来，统计了三类高频动作：回听定位（想确认某句话是谁说的）、 结论摘取（哪些是定了的，哪些只是聊过）、待办转录（谁做什么、什么时候）。这三件事占了整理时间的绝大部分， 也正好对应后面六个 Agent 里的后四个。

另一个观察来自工具使用习惯：团队已经在用在线文档，如果 AI 只能"整篇重写"，他们是不敢按下去保存的—— 因为不知道哪一句被改动了。这直接决定了我们要做"补丁级"的写作，而不是"一键生成文章"。

3　系统架构设计

3.1 总体架构

前后端分离，后端同时托管前端构建产物，这样"演示地址"只有一个，评审不需要配两个域名。 AI 相关逻辑全部收在 app/core 下，路由层只做参数校验与落库，方便单独测试和替换模型。

表现层　React 18 + TypeScript + Vite + Tailwind　｜　12 个页面路由、SSE 流式渲染、Diff 勾选交互、看板拖拽前的手动流转

3.2 为什么这样分层

最早我们把这些函数直接写在路由里，很快就遇到两个问题：一是换模型要改十几处；二是"某个 Agent 慢"这种问题 在日志里根本看不出来。拆出编排层之后，每次调用都会写一条 RunStep（输入摘要、输出摘要、token、耗时、 是否命中缓存、证据条数），前端的 Agent Trace 页面就是这个表的直接投影——它不是给评委看的装饰，是我们自己调优时的仪表盘。

3.4 会议分析流水线

六个 Agent 串成一条流水线，其中"抽决议"和"抽待办"两步并行，因为它们都只依赖分段结果，彼此没有先后关系。 串行的部分只保留真正有依赖的环节。

① scribe清洗转写、识别说话人、去掉口头语
② segmenter切议题，给每段打主题标签
③ decider抽决议/风险/未决问题 + 引文
④ planner抽待办：谁、做什么、何时
⑤ critic独立复核：证据是否支持、有无超范围
⑥ composer写成给人看的纪要正文
图 3-2　③④ 并行执行；⑤ 不是"再润色一遍"，而是带着质疑立场重读

失败时的降级路径

每个步骤都包在 try/except 里，任何一步失败都不会让整场会失败： 模型返回非法 JSON 会触发"契约自愈"（见 §4.3）重试两次；仍然失败则记一条 warning， 用规则兜底（例如摘要退化为"前三条决议拼接"）。界面上会显示"哪一步降级了"，而不是假装成功。

4　AI 技术方案

4.1 为什么是六个 Agent，不是一个大提示

我们最初写的是一个 1200 字的大提示词，一次调用产出"纪要 + 结论 + 待办"。它跑得通，但有三个硬伤：

  1. 无法定位错误。输出不对时，你不知道是没听清、没抽到，还是写歪了。
  2. 提示词互相干扰。"忠实摘要"和"大胆归纳"是两种语气，塞进一个提示词会互相稀释。
  3. 没法分级优化。清洗这种简单任务和大模型推理捆在一起，成本降不下来。

拆成六步之后，每一步都有独立的输入契约、输出契约和失败兜底；更重要的是，每一步可以单独挑模型档位—— 清洗用快模型、复核用大模型，这是成本能压到 $0.006 的前提。

反面经验：我们试过再加一个"格式化 Agent"专门把结果转成 JSON，最后删掉了。 格式化应该是代码的事，让模型重复输出一遍纯属浪费 token，还引入了新的不确定性。 这件事最后是靠统一的 call_json 契约解决的（§4.3）。

4.2 模型选型：用实测推翻了"大模型更准"的直觉

我们只接了一家供应商的两种模型：deepseek-flash（快）与 deepseek-v4-pro（强推理， 默认开启思维链）。直觉上"抽决议"这种需要判断的任务应该用 pro。于是写了一个对照脚本， 拿同一段 8 段转写、同一个 decider 提示词、max_tokens=4000，跑四种组合：

组合耗时输出 token抽出条数证据通过率
flash + 关闭思维链3.9 s5527100%
flash + 开启思维链7.7 s15177100%
pro + 关闭思维链6.4 s5586100%
pro + 开启思维链49.5 s4000（全部被思维链吃掉）0—
表 4-1　数据来自 scripts/bench_reasoning.py，结果落在 data/bench_reasoning.json

最后一行是关键：开启思维链的 pro 在 4000 token 预算内没能产出任何结果——思维链把预算耗尽， 正文为空，接口返回 finish_reason=length。这个现象在长提示词下非常容易踩到， 而它看起来像"模型抽不出东西"，而不是"预算不够"。

结论被固化进路由策略：抽取类任务统一用快模型并关闭思维链，质量不掉，延迟降一个数量级； 只有在"质量优先"档才让 decider / planner / critic / verifier 走 pro。这不是拍脑袋，是一个可复现的实验。

4.3 结构化输出契约：让模型输出可编程

所有需要结构化结果的调用都走 call_json(agent, system, user, ...)，它负责四件事：

  1. 容错解析。模型偶尔会在 JSON 前后加 ```json 围栏或一句解释，解析器先剥离围栏、再截取第一个 { 到最后一个 }。
  2. 预算自愈。如果 finish_reason == "length" 或正文为空，把 max_tokens 乘以 2.2（上限 8000）重试， 而不是把截断的半截 JSON 当结果往下传。§4.2 里 pro 的那个坑就是靠这条兜住的。
  3. 降级不静默。重试两次仍失败，抛 LLMFormatError，由调用方决定降级策略；同时把原始输出的前 200 字写进异常， 排查时不用复现。
  4. 记账。每次调用的 token、耗时、成本、是否命中缓存都写进返回的 meta，由编排层汇总成 Run。
def call_json(agent, system, user, *, temperature=0.2, max_tokens=1600, retries=2):
    for attempt in range(retries + 1):
        comp, provider = chat_safe(messages, model=..., json_mode=True, thinking=runtime.thinking_for(agent))
        text = _strip_fence(comp.text)
        if text:
            try:
                return _loads(text), meta          # meta 带 provider / thinking / tokens / cost
            except json.JSONDecodeError:
                last = text
        if comp.raw.get("finish_reason") == "length" or not comp.text:
            max_tokens = min(int(max_tokens * 2.2), 8000)   # 预算自愈
    raise LLMFormatError(f"{agent} 连续 {retries + 1} 次未返回合法 JSON；最后输出前缀：{last[:200]}")

4.4 证据链：把"看起来对"变成"查得到"

这是整个项目的技术核心。模型输出每条决议时必须附带 {segment_idx, quote}，代码在落库前做两步校验：

  1. 引文回查。用 difflib.SequenceMatcher 把 quote 与对应 segment 的原文比对，重合度低于 0.55 的条目直接丢弃。 这一步挡的是"模型自己编了一句很像的话"。
  2. 完整性判定。丢弃后如果某条决议没有剩余证据，它会被降级为 open_question（未决问题）， 而不是硬留成决议。界面上会显示"未决"标签，提示"这条需要人确认"。
阈值怎么来的：拿 120 条人工标注的引文对做扫描，阈值 0.45 时误留比例 11%，0.55 时降到 3.8%， 再往上会把口音重、转写有错的正常条目也误杀。0.55 是"漏"和"错"之间的折中，不是拍的。

演示数据里我们特意留了一条没有证据的条目——它来自一个跑题讨论，模型抽出了"要评估移动端"， 原文却没有任何人承诺。系统把它标成未决，评审时这是一个可以当场验证的点：点开看，确实没有引文。

4.5 混合检索与引用校验

知识库问答是"检索 + 生成 + 校验"三段。检索用 BM25（稀疏，认关键词）与向量（稠密，认语义）双路召回， 再用 RRF 融合排序，最后让 reranker Agent 结合问题重新排一次序，取前 6 段进上下文。 

score_rrf(d) = Σ_over_lists  1 / (60 + rank_list(d))

BM25      →  "0.55" / "阈值" 这类字面命中
向量(512d) →  "引用校验怎么定阈值" ≈ "引文重合度门槛" 这类换说法命中
RRF       →  两路都靠前的片段胜出，单路突兀的高分被压住
reranker  →  用问题重排，把"能直接回答"的片段提到前面

引用校验是这一段里最难做对的地方。最初我们用"回答句子与片段文本的序列相似度"判强/弱， 结果所有引用都被判成"弱"——因为回答是改写过的，字面重合天然低，这个方法没有区分力。 改成了两步：

  • 覆盖率 + 对比度。先算回答句子有多少字面片段出现在候选片段中（覆盖率）， 再把它与"和其他候选片段的平均覆盖率"比较，得到对比度 cover / (cover + baseline)。 真引用时对比度显著高于凑数引用，实测从"几乎全弱"变成"72% 强"。
  • 数字硬约束。如果回答句子里出现数字，该数字必须原文出现过，否则直接判弱。 模型编数字是引用场景里最常见的事故，这一条拦得很值。

4.6 语义缓存与四档路由

语义缓存解决"同一类问题反复问"：新问题的向量与历史问题余弦相似度 ≥ 0.95 时直接返回上次答案，并在界面上标明"命中缓存"。 阈值取 0.95 是保守选择——宁可少命中，也不要答非所问。演示数据里 31 次运行中有 26 次缓存命中， 这解释了为什么总成本只有 $0.075。

路由分四档，切换即时生效（写在 data/runtime.json，重启不丢）：

档位模型选择适用场景单场会成本
质量优先关键 Agent（decider/planner/critic/verifier）走 pro对外交付前跑一遍约 $0.02
均衡（默认）全部走 flash，关闭思维链日常使用约 $0.006
成本优先全部走 flash，温度与预算下调批量回溯历史会议约 $0.004
本地模型Ollama 兼容端点（qwen2.5 等）数据不出内网0（自建算力）

4.7 PII 脱敏网关

会议转写里经常出现手机号、身份证、银行卡、邮箱。脱敏网关在调用模型之前把四类实体替换成占位符 （<PHONE_1> 这类），模型返回后再按映射还原。它带来两个附加好处：

  • 审计友好。落库的是脱敏后的内容，日志里不出现真实号码；
  • 可度量。每条 Run 会记录本次掩码数量，界面上能看出"这场会有 3 处敏感信息"。

脱敏对模型效果几乎没有影响——它把注意力从"这是谁的电话"转移到"这里有一个号码"， 而后者才是纪要需要的语义。

5　核心功能实现

5.1 会议纪要：从转写到可追踪的决议

新建会议的入口接受两种输入：粘贴带时间戳的转写，或纯文本对话。前端会实时解析预览（识别 [mm:ss]、说话人： 前缀，无换行时按句聚合）， 确认后写入数据库再触发分析。分析默认走后台任务，页面每 2.6 秒轮询一次状态，不用干等。

详情页四个 Tab 是产品设计的重点：

Tab内容想解决的问题
纪要概览摘要、议题脉络（按话题聚类，每个话题带段落编号）、行动项没参会的人先看这一页就够
证据链按决议/风险/未决分组，每条带引文、说话人、时间点、置信度"凭什么这么说"当场可查
原始转写全文，点击决议可定位并高亮对应段落从结论跳回原话
Agent Trace六步执行链、每步输入输出摘要、token、耗时、质量指标出问题时知道哪一步歪了

导出支持 Markdown 与 Word（python-docx 生成，宋体 10.5，表格用 Light Grid Accent 1）， 导出的 Word 拿去直接发群里不用再排版。"转为任务"会把待办批量写进看板，并回写 task_id， 从此任务卡片上能看到"来源：Q3 产品路线评审会"。

5.2 智能写作：补丁，而不是重写

这里是产品观差异最大的地方。我们不让模型重写整篇文档。提示词明确要求它输出补丁列表： 

{"patches": [{"op": "replace | insert_after | delete",
              "target": "原文中连续存在的一段文字（8-60 字）",
              "new_text": "替换后的文本",
              "reason": "为什么这样改，30 字内"}],
 "style_note": "对全文风格的一句话点评"}

后端拿到补丁后逐条在原文里定位并应用（_apply_patches）， 然后对"原文 vs 修订稿"做行级 diff 得到编辑块。定位失败的补丁被跳过并记录，不会污染其他内容。 前端把每个编辑块渲染成一张卡片，默认勾选，用户可逐条取消，确认后调 apply 重建全文。

实测（文档《项目周报》301 字，四条指令）：补丁定位成功率 23/23 = 100%，平均耗时 11.2 秒。

为什么坚持补丁：办公文档里 80% 的句子是对的。整篇重写会把对的改坏、把语气改陌生， 用户不敢保存。补丁 + 差异卡片让"改了什么、为什么改"逐条可见，接受多少由人决定—— 这才是办公场景能落地的 AI 写作。

另外还叠了一层不花 token 的规则体检：平均句长、45 字以上长句数、程度副词密度、中英混排空格、重复标点、被动句。 这些规则既能进"文本体检"面板，也能在补丁之外提示"这里本来就有问题"。

5.3 知识库问答：流式 + 引用

上传支持 PDF / Word / Markdown / TXT / HTML，解析后按 Markdown 标题切段、再按长度切（目标 520 字，重叠 80 字）， 落库时记录页码与章节。问答走 SSE：先推一次 retrieval 事件（把召回片段先显示出来）， 再逐 token 推正文，最后推 done（含引用校验结果）。用户能立刻看到"它在查什么"， 而不是对着转圈等 7 秒。

引用卡片上标"强支撑 / 弱支撑"：强支撑说明这句话确实来自该片段，弱支撑提示"这条可能是模型自己的总结"。 这个标注比"显示来源"更有用——它让人知道哪句可以直接引用，哪句需要自己回查。

5.4 任务看板与工期预测

看板四列（待开始 / 进行中 / 待验收 / 已完成），卡片上有负责人、截止日、风险徽标和一条 P50/P90 进度条。 工期预测是一个轻量的对数正态模型，不是"猜一个数"： 

p50 = BASE_HOURS[priority] × 动词系数 × (1 + 依赖 0.18) × (1 + 负责人负载 0.08)
σ   = 0.34 + 0.16（描述 < 12 字）+ 0.10（有依赖）+ 0.08（含模糊动词，上限 0.85）
p90 = p50 × exp(1.2816 × σ)

模糊动词（调研、梳理、评估、优化、排查）会显著拉高 σ——因为这类任务的边界本来就不清楚， 给出一个确定数字反而是误导。看板上因此显示"2.9 / 5.0 天"而不是"预计 3 天"： 告诉使用者"大概率三天，但拖到五天的可能性不小"。

5.5 智能周报

周报页做成两段：数据面板秒出，正文按需生成。左侧面板（团队产出、本周会议、任务分布） 全部由本地规则聚合，不调模型；右侧正文点一下才生成，结果按"任务指纹"缓存， 数据没变就不重复花钱。这个设计是被一次事故逼出来的——最初把生成放在接口里同步执行， 用户打开页面要等 30 到 60 秒，看起来就是白屏。

5.6 运行观测

KPI（运行次数、token、成本、缓存命中）、14 天调用趋势、路由分配表、Agent 性能表（调用次数、token、平均耗时、 缓存、失败），以及逐次运行的 Trace 详情。这一页是我们自己排查问题的入口， 也是"成本可见"这条约束的落地方式。

7　创新点

7.1 技术创新点

（1）证据链纪要与"未决"降级机制

决议落库前必须通过引文回查（相似度 ≥ 0.55），否则降级为"未决问题"而不是假装成决议。 这让"哪些是定了的"变成可计算的事实，而不是整理者的判断。同类工具普遍只做"显示来源"， 我们把校验做进了写库路径。

（2）六 Agent 分工 + 独立复核（critic 的第二意见）

复核 Agent 的提示词是"你是质检员，唯一职责是找茬"，它不重写，只判断能不能入档。 并且我们在代码层给"判掉"加了权限边界：能判掉结论，不能判掉待办。 这是"模型判断 + 产品规则"的混合裁决，比纯模型或纯规则都稳。

（3）补丁级写作 + 逐块接受

模型只输出 {op, target, new_text, reason}，代码负责定位与应用， diff 负责呈现。定位失败只丢这一条。实测 23/23 补丁全部命中，用户可按块接受。 它把"AI 改写文档"从不可控的全量替换，变成可控的、可审计的编辑建议。

（4）对比度引用校验（覆盖率 + 数值硬约束）

用"与目标片段的覆盖率相对于其他片段的对比度"判强弱，再加"数字必须在原文出现"的硬约束。 这解决了改写型回答在字面相似度下全被判弱的问题，实测支撑率从近似 0 提升到 72.2%。

（5）语义缓存 + 四档模型路由 + 预算自愈

三件事共同把成本压到 $0.006/场：缓存挡住重复咨询，路由把简单任务交给快模型， 预算自愈拦住"思维链吃光预算导致空输出"这类静默失败。其中"pro 开思维链在 4000 token 内产出 0 条" 是我们自己测出来的反直觉结论，已经固化进默认策略。

7.2 应用创新点

（6）会议 → 任务 → 周报的闭环

待办从会议里长出来，带着证据进看板，周报再从看板聚合。这条链路让"会上说的"和"这周做的" 第一次对得上——任务卡片上能看到来源会议，周报能算出覆盖率（哪些任务有明确负责人和截止日）。

（7）Agent Trace 作为产品功能（而不是运维日志）

普通用户也能看到六个 Agent 每一步做了什么、花了多少、证据通过几条。它把"黑箱"变成"可解释"， 也让"AI 帮了多少忙"从主观感受变成可截图的数字（例如"证据覆盖率 93%，评审打分 88"）。

（8）P50/P90 双值工期与风险可视化

不用单一预计时间，而是给区间：p50 是"大概率"，p90 是"要做好拖到这时候的准备"， 模糊动词会显著拉宽区间。看板上用进度条呈现，负责人一眼能看出哪张卡最危险。

（9）脱敏网关 + 成本可见，让 AI 敢在真实办公场景用

敏感信息在出网前替换、返回后还原；每一分钱花在哪个 Agent 上都可查。 这两件事不是功能点，是"团队敢不敢把它放进日常工作流"的前提。

8　总结与展望

这个项目里我们花时间最多的不是写页面，而是三件"看不见"的事： 让模型输出可校验（证据链、引用校验）、让失败可降级（契约自愈、每步兜底）、 让成本可控（路由、缓存、并行）。它们不出现在界面上，但决定了这个工具能不能被真实团队用起来。

过程中被数据推翻的判断至少有三次：以为 pro 更准（实测同一任务 flash 抽得更多）、 以为引用校验用相似度就够（实测全判弱）、以为 critic 越严格越好（实测把待办全判掉了）。 每次修正都写进了代码注释——这也是我们坚持"保留完整 Git 历史"的原因：判断是有代价的，应该留下痕迹。

下一步的三件事：把长会议做成层次摘要（map-reduce），把语音转写接进来自建闭环， 把知识库从"问答"扩展到"主动提醒"（例如发现新决议与旧文档冲突时提示）。 再往后，我们希望它变成团队的"记忆层"——不是替人做决定，而是让每个决定都留得下证据。
